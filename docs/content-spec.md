# コンテンツ仕様

## 1. 管理方針

問題とフレーズは、TypeScriptファイル内の型付き静的データとして管理する。MVPではAPI、データベース、CMSを使用しない。5カテゴリの各5問題に、それぞれ3件のフレーズを追加する。電車・駅の日本語、ローマ字、英訳は2026-08-05にプロジェクトオーナーが確認済みである。追加4カテゴリの初期データは2026-08-11に追加し、公開前の人間確認を必要とする。音声は後続工程とする。

場面選択用のカテゴリ概要もTypeScriptの静的データとして管理する。`train-station`、`airport`、`restaurant`、`hotel`、`shopping` の5件をすべて選択可能にする。

## 2. カテゴリデータの構造

カテゴリ概要は、`id`、英語タイトル、短い英語説明、遷移先を持つ。

```ts
export type CategorySummary = {
  id: string;
  title: string;
  shortDescription: string;
  href: string;
};
```

## 3. 問題データの構造

1問題は次を持つ。

- `slug`: URLに使用する一意な識別子
- `title`: 問題一覧・詳細に表示する英語タイトル
- `shortDescription`: 一覧カード向けの短い英語説明
- `status`: 詳細を利用可能であることを示す公開状態。現在は全問題で `available` とする
- `situation`: 詳細画面向けの英語状況説明
- `phrases`: 3〜5件のフレーズ
- `staffMessage`: 問題全体に対応する駅員向けメッセージ

各フレーズの `Show to staff` は、そのフレーズ自身の日本語と英訳を表示する。`staffMessage` は問題全体を一文で伝える将来または補助用途のデータとして保持し、現在のUIでは使用しない。

## 4. フレーズデータの構造

1フレーズは次を持つ。

- `id`: 問題内で一意な識別子
- `japanese`: 利用者が話す、または駅員へ見せる日本語
- `romaji`: 日本語の読み方
- `english`: 意味を説明する自然な英語
- `audioPath`: 音声追加時に設定する、`public` を基準としたMP3の任意の公開パス

各問題は3〜5件のフレーズを持つ。フレーズは、利用者が最初に伝える文、確認する文、必要に応じて補足する文のように、現場で使う自然な順序に並べる。

## 5. TypeScriptの型定義案

最低限、次の型を使用する。

```ts
export type Phrase = {
  id: string;
  japanese: string;
  romaji: string;
  english: string;
  audioPath?: string;
};

export type Problem = {
  slug: string;
  title: string;
  shortDescription: string;
  situation: string;
  phrases: Phrase[];
  staffMessage: {
    japanese: string;
    english: string;
    audioPath?: string;
  };
};
```

データ配列は `satisfies readonly Problem[]` などを使って形を検査しつつ、slugの推論を保つ案を推奨する。ただし、配置ファイル名と補助関数の構成は実装時に単純さを優先して決める。

## 6. slugとIDの命名規則

### slug

- 小文字の英単語とハイフンだけを使う kebab-case とする。
- 状況が短く理解でき、MVP内で重複しない値にする。
- 公開後はURL互換性のため安易に変更しない。
- 電車・駅の5問題では `cannot-exit-gate`、`wrong-train`、`cannot-find-platform`、`insufficient-ic-balance`、`lost-item-on-train` を使用する。

### フレーズID

- 問題内で一意な、ゼロ埋め2桁の連番文字列を基本とする。
- 推奨形式は `{problem-slug}-{phrase-number}` とする。
- 例: `cannot-exit-gate-01`
- 配列内の順序と番号を一致させる。

## 7. 日本語表現のルール

- 駅員に対して失礼にならず、旅行者が発話・提示しやすい短い表現にする。
- 教科書的な直訳より、駅の現場で自然に通じる表現を優先する。
- 一文に情報を詰め込みすぎない。
- 必要な主語は省略できるが、誰の状況か曖昧になる省略は避ける。
- 漢字を使う場合も、ローマ字と音声で補える内容にする。
- 句読点、全角・半角、丁寧さの水準をデータ全体で統一する。
- 公開前に日本語母語話者または同等の能力を持つ人が、自然さと状況適合性を確認する。

## 8. 英訳のルール

- 日本語の用途を利用者が誤解しない、自然で簡潔な英語にする。
- 単語ごとの直訳より、発話意図が一致する訳を優先する。
- 問題タイトル、説明、フレーズ訳で同じ用語を一貫して使う。
- 地域限定の俗語や不必要に難しい表現を避ける。
- 日本語との差異が安全性や行動に影響する場合は公開しない。

## 9. ローマ字表記のルール

- 表記方式は修正ヘボン式を基本とし、長音は可能な範囲でマクロン（`ō`、`ū` など）を使用する。
- 英語話者が再現しやすい読みを優先し、データ内で一貫させる。
- 文頭だけを大文字にするなど、大文字・小文字の規則を統一する。
- 助詞の発音（例: `は` を `wa`）は実際の読みを表す。
- 長音、促音、撥音、固有名詞は、人間による音声との照合を行う。

## 10. 音声ファイル（後続対応）

現在のUIでは音声を提供しない。将来追加する場合は、以下の方針を使用する。

### 保存場所

```text
public/audio/train/
```

### 命名規則

```text
{problem-slug}-{phrase-number}.mp3
```

例:

```text
cannot-exit-gate-01.mp3
wrong-train-01.mp3
```

`audioPath` は `/audio/train/cannot-exit-gate-01.mp3` のように先頭 `/` を付ける。ファイル名のslugと番号は対応する問題・フレーズIDに一致させる。音声は開発時に無料または無料枠のあるText-to-Speechサービスで一度だけ生成するが、利用サービス、話者、速度、音量、再生成手順は未確定であり、特定サービスを確定事項にしない。

`staffMessage.audioPath` を用意する場合の命名規則は未確定。フレーズ音声と重複するなら同じパスを参照する。

## 11. 公開前の人間による確認

- 25問題のタイトルと説明が実際の状況を正確に表す。
- 各問題が3〜5件のフレーズを持ち、重複や不要な表現がない。
- 日本語が自然、丁寧、短く、各カテゴリの現場で通じる。
- 英訳が日本語の意図と一致する。
- ローマ字が日本語の読みと一致し、表記規則が統一されている。
- 音声追加時は、MP3の発音と音質、音声パス、ファイル名、slug、ID、連番を別途確認する。
- 不適切、差別的、危険、誤解を招く表現がない。
- 実際の旅行場面を想定し、スタッフへ見せても意味が通る。
